# Codex App Server integration

`CodexAppServerManager`는 탐색된 실행 파일을 argv 기반 `cross-spawn(executable, ['app-server','--stdio'])`로 시작한다. Shell 문자열을 만들지 않는다. stdio JSONL은 줄 단위로 파싱하고 증가 Request ID, correlation map, timeout을 사용한다. App Server request pending map(기본 100개)과 stdin outbound 큐(기본 100개)는 서로 다른 상한으로 관리한다. stdin이 막히면 `CODEX_STDIN_BACKPRESSURE`를 반환하여 요청 폭주와 파이프 backpressure를 혼동하지 않는다. malformed JSON 제한, crash 감지, 제한된 지수 backoff 재연결, 앱 종료 시 graceful shutdown 후 Windows process tree 정리를 제공한다.

프로토콜 경계의 runtime schema와 버전/기능 협상은 [`src/main/codex/protocol-adapter.ts`](../src/main/codex/protocol-adapter.ts)에 모아 둔다. 현재 지원 fixture 버전은 `v1`이며, initialize 응답에 protocol version이 없는 구버전은 v1 메시지 shape 호환으로 간주하고, 명시적으로 지원하지 않는 버전은 `CODEX_PROTOCOL_UNSUPPORTED`로 종료한다. initialize에는 앱의 client identity/version, 지원 protocol versions, 기능 flags를 보내며 `manager.protocolInfo`에서 서버 identity/version, negotiated feature flags, `codex-app-server` provenance를 조회할 수 있다. Codex CLI generated schema를 빌드 시 호출할 수 없는 환경에서는 이 adapter의 fixture/version 인터페이스를 사용해 fixture를 교체하고 통합 테스트로 검증한다.

초기화 순서는 `initialize` → `initialized` → 병렬 `account/read`, `model/list`다. 모델 ID는 하드코딩하지 않고 `isDefault`, 기본/지원 Reasoning Effort, 이미지 입력 기능을 동적으로 반영한다. 새 보고서의 고급 설정은 조회된 모델과 해당 모델이 실제 광고한 Effort만 표시하며 선택값을 보고서 옵션에 저장한다. 로그인은 `account/login/start`의 ChatGPT browser flow URL만 HTTPS 외부 브라우저로 연다. API Key 입력 UI와 인증 파일 읽기는 없다.

Thread는 Chat/Report AI session별로 SQLite에 저장하며 Renderer는 thread ID를 전송하지 않는다. Main이 `sessionId`로 DB의 thread를 조회하고, 현재 App Server generation에 로드되지 않은 기존 thread는 `thread/resume` 후 turn을 시작한다. Resume 실패 시 새 thread로 조용히 전환하지 않고 `CODEX_THREAD_RESUME_FAILED`로 중단하여 대화가 분기되지 않게 한다. Chat turn은 해당 `chats/<session>/agent-work`를 사용한다. Report turn은 report 디렉터리를 읽기 기준(`cwd`/`runtimeWorkspaceRoots`)으로 사용하지만 쓰기 권한은 `reports/<report>/agent-work/output`으로만 제한한다. 따라서 `source-originals`, `source-extracted`, `evidence`에는 Codex가 쓸 수 없다. 모든 turn은 `approvalPolicy: never`, network disabled, environments disabled로 시작한다. `danger-full-access`는 사용하지 않는다. 스트리밍은 `item/agentMessage/delta`, 완료는 `turn/completed`, 취소는 `turn/interrupt`를 사용한다. 완료 시 `turn.items`의 `final_answer` Agent Message를 권위 있는 결과로 사용하여 중간 commentary와 최종 응답이 결합되지 않게 한다. Structured Output은 JSON Schema를 `outputSchema`로 보내며, 계획/생성 스키마의 Source ID는 Main이 해당 report의 실제 Source ID enum으로 제한한다. Source가 없으면 근거 배열의 `maxItems`를 0으로 설정한다. Markdown fence나 앞뒤 설명이 있는 호환 응답도 마지막 Schema-valid JSON만 추출한 뒤 Zod/HTML 정화를 거친다. 생성 화면에는 원시 JSON 대신 진행 상태와 수신 크기만 표시한다.

Turn 시작은 첫 비동기 경계 전에 Main 프로세스가 `starting` reservation을 잡으므로 동시 시작은 `CODEX_BUSY`로 차단한다. Main은 Codex provider catalog와 DB session 설정을 기준으로 model/effort를 결정·검증하며 Renderer 값은 힌트일 뿐이다. task/stream record도 `startTurn` 전에 등록하므로 빠른 완료가 유실되지 않고, terminal DB/message 처리는 task별 한 번만 수행한다. 취소 IPC는 선택적인 `taskId`/`sessionId`를 받아 현재 reservation과 상관성을 확인한다. 스트림/완료 notification은 실제 `threadId`와 `turnId`가 현재 reservation과 일치할 때만 전달한다. 완료/실패/취소/프로세스 종료는 terminal tombstone으로 멱등 처리하고, 취소 뒤 도착한 late notification은 폐기한다. 필수 필드가 빠진 `turn/completed`는 성공으로 간주하지 않고 `CODEX_PROTOCOL_ERROR`로 종료한다. 프로세스 listener와 pending request에는 generation을 부여하여 이전 프로세스의 stale response/exit가 재시작된 프로세스를 건드리지 못하게 한다.

CLI 버전별 알 수 없는 응답 필드는 무시하고 필요한 필드만 Zod로 확인한다. Structured Output용 object schema는 모든 `properties`를 `required`에 포함하고 `additionalProperties: false`를 유지한다. 이 계약은 재귀 단위 테스트와 실제 Codex smoke test로 고정한다. Structured Output은 최대 1MB까지만 JSON/간이 JSON Schema로 확인하며, 한 번의 bounded parse에 실패하면 원문/오류 payload를 저장하거나 stream하지 않고 `CODEX_PROTOCOL_ERROR`를 발생시킨다. 필요한 경우 상위 계층이 새 turn을 명시적으로 재시도할 수 있지만 manager가 원문을 repair prompt에 재주입하지는 않는다. App Server가 없으면 TUI나 `codex exec`로 우회하지 않고 업데이트 필요 상태를 표시한다. Turn 실패의 provider payload는 Renderer나 로그로 전달하지 않고 schema/context/usage/auth/sandbox/overload 범주의 안전한 오류 코드와 메시지로 변환한다.

JSON-RPC `-32001` overload만 retryable로 분류한다. 기본 최대 3회 시도, exponential delay(100ms, 200ms, 최대 2s)와 full jitter를 사용하며, 생성자에 `sleep`, `random`, 시도/지연 상한을 주입해 결정론적으로 테스트할 수 있다. protocol response/notification, model/account/turn 완료 메시지는 모두 adapter runtime schema를 통과해야 한다. start/refresh/stop은 single-flight와 generation token을 통해 lifecycle 재진입을 차단하고, 이전 generation의 늦은 response/exit는 새 프로세스에 영향을 주지 않는다.
